# 第4章 系统设计

## 4.1 系统功能设计

### 4.1.1 扫描功能模块设计

扫描功能模块是 NeonScan 2.0 的基础能力层，负责完成端口扫描、目录扫描、POC 扫描、EXP 执行、Web 探测与 WAF 绕过等核心任务。各模块均采用统一的 HTTP 接口接收请求，由后端创建任务对象并通过 SSE 事件流向前端实时推送进度和结果，从而避免前端轮询造成的额外开销。

端口扫描模块支持 TCP/UDP 两种协议，允许用户配置端口范围、并发数、超时时间和 Banner 抓取选项。目录扫描模块支持多字典并发处理与工作池模式，能够判定状态码并记录响应长度、重定向位置等信息。POC 扫描模块兼容 Legacy、X-Ray 与 Nuclei 子集三种规则格式，通过统一表达式引擎完成请求构造与响应匹配。EXP 执行模块支持多步骤利用链、变量提取、变量替换、Cookie 贯穿、步骤验证与重试。Web 探测模块用于构建目标画像，WAF 绕过模块则通过多种变形策略寻找可用入口。

这些功能模块并不是孤立存在，而是围绕统一任务流进行组织：扫描结果既可以直接展示，也可以继续作为 AI 自动扫描、EXP 生成与报告汇总的输入，形成后续的联动分析能力。

### 4.1.2 资产收集模块设计

NeonScan 2.0 将资产收集模块设计为由外部工具驱动的组合式发现链路，而非仅提供单一的“JS 扫描”能力。系统当前集成的核心工具包括 FFUF、URLFinder 和 Packer-Fuzzer，它们分别承担隐藏路径发现、URL/JS 链接提取与打包前端资源解包尝试等任务。

模块首先对目标进行可解包性分析，判断页面中是否存在 webpack、vite、rollup 等打包痕迹；若具备条件，则调用 Packer-Fuzzer 进行 JS 解包和静态资源挖掘。与此同时，系统可以利用 FFUF 对潜在路径进行探测，发现未显式暴露的静态文件和接口入口；再通过 URLFinder 提取 HTML 与脚本中的 URL、接口和 JS 链接。最终结果统一进行合并、去重和分类，按 js、api、other 三类输出，并支持一键回流到目录扫描、POC 扫描和 Web 探测模块。

因此，资产收集模块在本系统中的作用不只是补充信息，而是整个扫描闭环的起点，为后续验证和利用生成提供高价值输入。

### 4.1.3 MCP 集成模块设计

系统的 MCP 集成模块用于补充传统 Web 扫描之外的分析能力。在当前 2.0 版本中，代码层已经明确落地的是 JADX MCP 会话模型，而不是将 IDA Pro 作为与其并列的主流程实现。后端暴露的 MCP 路由集中于 `/mcp/jadx/connect`、`/mcp/jadx/configure`、`/mcp/jadx/chat/stream`、`/mcp/jadx/messages`、`/mcp/jadx/status` 等接口，说明当前实现重点是围绕 APK 反编译分析与会话管理展开。

该模块采用统一会话抽象设计。每个 JADX 会话包含会话 ID、API 类型、消息历史、MCP 连接状态、最近活动时间等信息，底层使用 `ChatSession` 接口和 `BaseChatSession` 结构体统一管理。`JADXMCPConnection` 负责维护与 MCP 服务端的 HTTP 通信、工具列表、连接状态和请求序号，支持在会话范围内进行工具调用和流式交互。

这一设计使得移动应用反编译分析能够纳入与 Web 扫描相同的任务和会话管理框架，便于前端统一展示连接状态、消息记录和分析结果。

### 4.1.4 AI 分析模块设计

AI 模块是 NeonScan 2.0 的关键升级点。系统不再仅将 AI 用于扫描报告总结，而是进一步将 AI 引入自动扫描编排、Python EXP 生成、失败分析、自动验证与迭代修正等核心流程。

AI 模块首先通过统一的 `AIProvider` 接口兼容 DeepSeek、OpenAI、Anthropic、Ollama 等不同提供商，屏蔽不同模型调用接口之间的差异。其次，系统实现了 AI 自动扫描工作流：AI 根据当前目标与已知结果决定调用端口扫描、Web 探测、POC 扫描等内部工具，并将结果继续纳入上下文，形成迭代式自动化分析过程。

在利用生成层面，系统可将 POC 扫描结果归一化为 `ExpSpec`，再由 AI 生成 Python 利用脚本；同时支持批量生成多个 Python EXP。更进一步，系统会将生成结果送入自动验证模块，执行脚本、分析失败原因、请求 AI 修正并重试，直至验证成功或达到最大次数。由此，AI 模块在 2.0 中已经从“分析辅助”演进为“扫描编排 + 利用生成 + 自动修正”的综合智能能力层。

## 4.2 系统架构设计

NeonScan 2.0 采用 B/S 架构，前端由静态 HTML、CSS、JavaScript 页面组成，后端采用 Go 单进程 HTTP 服务。前端负责参数输入、任务发起、实时进度展示、报告汇总和状态恢复；后端负责统一路由注册、任务管理、扫描执行、AI 调度、MCP 会话管理与文件隔离存储。

系统架构可分为四层。第一层为前端交互层，包括端口扫描、目录扫描、POC 扫描、EXP 执行、Web 探测、WAF 绕过、资产收集、AI 分析、JADX MCP、报告页等多个独立页面。第二层为 HTTP 接口与任务调度层，由 `main.go` 中的路由与 `Task`/`SSEMessage` 机制构成，负责将长任务统一封装为可跟踪、可停止、可回收的执行单元。第三层为能力执行层，包括各类扫描模块、AI 模块、JADX MCP 会话模块与外部工具调用逻辑。第四层为资源与状态层，包括上传目录、临时生成的 Python EXP、前端 localStorage 状态以及运行时会话与任务表。

系统采用统一的数据回流理念：资产收集结果能够回流到目录扫描、POC 扫描与 Web 探测；POC 扫描结果能够归一化为 `ExpSpec` 进入 AI 生成与验证流程；各模块最终结果统一汇聚到报告页面。系统同时配备 Janitor 机制，定期清理老任务、上传目录与会话，避免长时间运行带来的资源堆积问题。

## 4.3 数据结构设计

本系统的数据结构以运行时任务对象、请求对象、规则对象、AI 会话对象和逻辑资源对象为核心，而不是传统数据库表结构。由于当前实现并未引入独立数据库持久化层，因此更适合用“逻辑数据模型”描述模块之间的数据关系。

任务管理方面，`Task` 结构体用于保存任务 ID、总数、已完成数、创建时间、消息通道和停止信号；`SSEMessage` 结构体用于统一描述前端接收的消息类型、任务 ID、进度文本、百分比和具体数据载荷。两者共同构成系统的统一异步执行与实时反馈模型。

AI-EXP 相关数据结构是 2.0 的新增重点。`AIGenPythonFromExpReq` 用于描述单个 Python EXP 生成请求，包含 AI 提供商、目标地址、EXP 规范、自动验证开关等信息；`AIGenPythonFromExpBatchReq` 用于批量生成请求；`ExpVerifyConfig` 用于自动验证配置，包含目标地址、ExpSpec、Python 代码、漏洞类型、重试次数和超时时间；`VulnCategory` 用于对漏洞进行分类，从而生成更有针对性的提示词和测试命令。

在 AI 与 MCP 抽象方面，`AIProvider` 接口统一了不同模型服务的聊天调用方式；`ChatSession` 接口和 `BaseChatSession` 结构体统一描述会话 ID、API 信息、消息列表、MCP 连接和活动时间；`JADXMCPConnection` 结构体则维护与 JADX MCP 服务端的连接状态、工具列表与请求上下文。

在逻辑资源层面，系统还存在上传文件资源、报告汇总结果、前端表单状态、运行中任务映射、临时生成 EXP 文件等运行时对象。这些对象通过文件目录和内存结构进行管理，是系统实现可追踪、可回放和可清理能力的重要基础。
