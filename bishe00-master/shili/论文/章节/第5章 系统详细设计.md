# 第5章 系统详细设计

## 5.1 任务管理模块的详细设计实现

对应文件：`main.go`

任务管理模块是 NeonScan 2.0 的基础支撑层，负责统一管理所有长耗时任务的创建、进度统计、实时消息推送、停止与清理。系统在后端定义 `Task` 结构体保存任务 ID、总数、完成数、创建时间、SSE 通道和停止信号，并通过 `SSEMessage` 结构体统一描述事件消息。

当用户在前端发起端口扫描、目录扫描、POC 扫描、EXP 执行、AI 自动扫描或批量生成等耗时操作时，后端首先调用 `newTask` 创建任务实例，再将任务登记到全局任务表中。执行过程中，各模块通过 `IncDone` 更新完成计数，通过 `safeSend` 将 `progress`、`find`、`end` 等类型的消息推送给前端。用户如果中途停止任务，则通过 `/task/stop` 接口触发停止信号。后台还会定期清理超过阈值的老任务，避免内存长期堆积。

这种统一的任务机制使系统中不同类型的耗时操作能够共享相同的生命周期管理模型，也为后续报告汇总、任务恢复和 AI 自动编排提供了基础。

## 5.2 端口扫描模块的详细设计实现

对应页面：`ports.html`  
对应处理器：`portScanHandler`

端口扫描模块用于识别目标主机开放的 TCP 或 UDP 端口，并可选择抓取基础 Banner 信息。前端页面允许用户输入目标地址、端口范围、并发数、超时时间和扫描类型；后端收到请求后解析端口列表，创建任务并使用 goroutine 并发执行端口探测。

实现时，系统通过信号量控制并发数。对于 TCP 扫描，模块使用 `net.DialTimeout` 建立连接并在必要时读取返回数据作为 Banner；对于 UDP 扫描，模块使用 `net.DialUDP` 发送探测数据并尝试读取响应。每个端口探测完成后，系统计算当前进度并推送消息；若发现开放端口，则通过 `find` 事件将端口号、协议类型和 Banner 等信息返回给前端。

该模块的实现方式兼顾了扫描效率与前端可视化反馈，是系统最基础的资产发现能力之一。

## 5.3 目录扫描模块的详细设计实现

对应页面：`dirs.html`  
对应处理器：`dirScanHandler`

目录扫描模块用于发现目标站点中的有效路径和敏感资源入口。前端支持选择内置字典或上传自定义字典，并可配置并发数和超时时间。后端接收请求后，读取字典文件内容，将路径集合送入工作池并发处理。

工作池中的每个 worker 负责拼接请求 URL、发送 HTTP 请求并分析响应。系统将状态码 200、301、302、403 视为有效结果，并额外记录响应长度与 `Location` 字段，便于后续人工验证和报告引用。扫描过程中，模块持续向前端推送当前进度和命中的有效路径。

目录扫描结果不仅可直接展示，还能与资产收集和 POC 扫描结果结合，作为 AI 自动扫描和漏洞验证的重要上下文输入。

## 5.4 POC 扫描模块的详细设计实现

对应页面：`poc.html`  
对应处理器：`pocScanHandler`

POC 扫描模块用于对目标站点进行规则化漏洞验证。系统当前兼容 Legacy、X-Ray 风格和 Nuclei 子集三种规则格式，并通过统一的数据流输出命中结果。前端支持上传规则文件、选择规则目录并配置目标、并发数和超时时间；后端则负责解析规则、执行请求、匹配响应并实时返回结果。

### 5.4.1 Legacy 格式解析实现

Legacy 格式适合描述结构较直接的验证逻辑，通常包含 `method`、`path`、`body`、`headers` 和匹配规则等字段。系统读取 YAML 或 JSON 规则文件后，将其解析为内部结构体，再根据规则内容构造请求并检查状态码、响应体或响应头是否命中条件。

这种格式实现简单、适合作为基础规则输入，在项目中承担了大量直接验证任务。

### 5.4.2 X-Ray 表达式引擎实现

X-Ray 风格规则强调逻辑表达式能力，能够将状态码、响应体关键词、响应头信息等条件进行布尔组合。系统读取规则后，先执行规则中定义的请求，再将响应数据送入表达式求值过程，支持 `and`、`or`、`not` 等逻辑运算。

这种实现方式提升了规则表达能力，使系统能够处理更复杂的多条件命中场景。

### 5.4.3 Nuclei 子集解析实现

Nuclei 子集格式包含请求列表和匹配器列表，支持 `word`、`status`、`dsl` 等匹配方式，并允许通过 `and/or` 配置匹配器组合关系。系统按顺序执行请求，汇总响应，再依据匹配器规则判断是否命中。

通过对三类规则格式的兼容，NeonScan 2.0 在不依赖外部规则引擎的情况下，已经能够覆盖常见的漏洞验证需求，同时为后续 AI-EXP 生成提供统一的命中结果输入。

## 5.5 EXP 执行模块的详细设计实现

对应页面：`exp.html`  
对应处理器：`expExecHandler`

EXP 执行模块用于完成多步骤利用链验证。系统使用 `ExpSpec` 描述利用过程，每个步骤可以定义请求方法、路径、请求体、请求头、变量提取规则和验证条件。执行时，后端按顺序发送请求，并在步骤之间维护变量表和 Cookie 状态。

如果某一步骤中定义了 `bodyRegex` 或 `headerRegex`，系统会从响应中提取变量写入上下文，以便后续步骤通过 `{{var}}` 占位符进行替换。模块还支持重试、等待、步骤级命中判断等机制，使其能够描述更加贴近真实攻击链的验证过程。若所有关键步骤完成并通过验证，则向前端输出成功结果。

该模块既可以独立使用，也可以作为 AI 生成 Python EXP 之前的人工验证参考。

## 5.6 Web 探测模块的详细设计实现

对应页面：`probe.html`  
对应处理器：`webProbeHandler`

Web 探测模块用于构建目标画像。前端支持批量输入 URL，并可选择启用 favicon 检测和 robots.txt 检测。后端收到请求后，会先对 URL 去重并补全协议，再并发发起请求，提取标题、状态码、协议、内容长度等基本信息。

在响应分析阶段，系统会结合 `Server`、`X-Powered-By`、Cookie 特征、页面内容和 favicon SHA1 等信息识别技术栈与指纹特征。探测结果可为后续 POC 选择、WAF 绕过和 AI 自动扫描决策提供依据。

## 5.7 WAF 绕过模块的详细设计实现

对应页面：`waf.html`  
对应处理器：`wafBypassHandler`

WAF 绕过模块通过对输入载荷进行多种变形并测试结果可用性，以辅助发现存在防护绕过空间的请求方式。系统支持大小写变形、URL 编码、双编码、路径填充、参数分割、无害头注入等策略，并允许与多种 HTTP 方法组合测试。

后端会对每个原始 payload 生成变体集合，逐一构造请求并发送到目标地址，再依据状态码或关键字命中结果判断是否存在可用入口。该模块能够帮助用户快速筛选更具利用价值的输入方式。

## 5.8 资产收集模块的详细设计实现

对应页面：`shouji.html`  
对应处理器：`internal/shouji/shouji.go` 中注册的相关路由

资产收集模块是 NeonScan 2.0 与传统扫描工具相比的重要增强点。模块围绕可解包性分析、FFUF 路径发现、URLFinder 链接提取和 Packer-Fuzzer 解包尝试构建统一数据流。

系统首先通过 `AnalyzePackable` 对目标页面进行可解包性分析，检查页面是否包含 webpack、vite、rollup 等打包特征；若满足条件，则调用 Packer-Fuzzer 辅助提取隐藏的接口和资源信息。随后，系统可调用 FFUF 对潜在路径进行爆破，调用 URLFinder 抓取 URL 和 JS 链接。最后，通过 `MergeResults` 对各来源结果统一去重和分类，并将其标记为 js、api、other 三类输出。

这些结果既可以直接展示，也可以一键导入目录扫描、POC 扫描和 Web 探测模块，显著提升整体扫描命中率和闭环效率。

## 5.9 MCP 集成模块的详细设计实现

对应页面：`jadx_mcp.html`  
对应处理器：`internal/mcp` 下的 JADX 相关 Handler

NeonScan 2.0 中已落地的 MCP 集成重点是 JADX 会话分析能力。系统围绕 `JADXMCPConnection`、`ChatSession` 和 `BaseChatSession` 组织连接状态、消息历史、会话活动时间和工具调用关系，使 APK 反编译分析能够在统一界面内完成。

### 5.9.1 JADX MCP 连接与会话管理实现

系统通过 `/mcp/jadx/connect` 建立与 MCP 服务端的连接，通过 `/mcp/jadx/configure` 写入会话参数，并使用 `GetOrCreateJADXSession` 获取或创建当前会话对象。每个会话都维护唯一的 `sessionId`，并记录所使用的 API 类型、API Key、消息列表和 MCP 连接对象。

`JADXMCPConnection` 负责与 MCP 服务端通信，维护基础地址、HTTP 客户端、连接状态、可用工具列表和请求序号。这种设计使同一前端页面能够在多次请求之间共享上下文，避免每次都重新初始化分析状态。

### 5.9.2 JADX MCP 状态查询与流式对话实现

系统通过 `/mcp/jadx/messages` 获取指定会话的消息历史，通过 `/mcp/jadx/status` 查询当前会话的连接状态、消息数量、是否已配置 API 信息等元数据，并通过 `/mcp/jadx/chat/stream` 实现流式分析输出。前端据此可以展示连接结果、历史消息和实时推理内容。

与传统静态结果返回方式相比，流式会话模型更适合反编译分析这种交互式场景，也更符合系统“统一会话、统一反馈”的总体设计目标。

## 5.10 AI 分析模块的详细设计实现

对应页面：`ai_analysis.html`  
对应处理器：`aiAnalyzeHandler`、`aiAutoScanHandler`、`aiGenPythonFromExpHandler`、`aiGenPythonFromExpBatchHandler`

AI 分析模块是 2.0 版本中变化最大的部分。系统通过统一的 `AIProvider` 抽象屏蔽多家模型服务调用差异，并在此基础上实现自动扫描、利用生成与自动验证闭环。

### 5.10.1 AI 自动扫描编排实现

`aiAutoScanHandler` 用于接收目标地址和 AI 配置，随后构建 AI 上下文和工具列表。AI 根据当前分析结果决定调用哪些内部扫描能力，例如端口扫描、Web 探测、POC 扫描等。每一轮工具调用结果都会被重新纳入对话上下文，驱动下一轮决策。

这种设计使系统从“用户手动点选模块”扩展到“AI 协调多个模块形成自动工作流”，体现出 2.0 版本的智能化特征。

### 5.10.2 Python EXP 生成与批量生成实现

当 POC 扫描命中后，系统可以将结果归一化为 `ExpSpec`。`aiGenPythonFromExpHandler` 用于生成单个 Python EXP，支持根据漏洞类型构造差异化提示词，并可结合目标地址、验证信息和利用建议优化输出。`aiGenPythonFromExpBatchHandler` 则支持并发批量生成多个 Python EXP，通过任务模型统一返回进度与结果。

在生成过程中，系统不仅要求脚本能完成请求发送，还要求其遵守统一输出标记、变量替换、URL 拼接和 Windows 兼容要求，以便后续自动验证过程稳定运行。

### 5.10.3 自动验证与迭代修正实现

自动验证模块由 `ai_exp_verify.go` 提供核心实现。系统首先通过 `DetectVulnCategory` 对漏洞类型进行分类，再根据不同类型选择测试命令、系统提示词和验证逻辑。`GenerateAndVerifyExp` 会把当前 Python EXP 写入临时文件，实际执行脚本并分析其输出是否满足成功标记、命中条件和回显提取要求。

如果验证失败，系统会调用 `analyzeFailure` 分析失败原因，再由 `buildCorrectionPrompt` 构造修正提示词，请求 AI 输出新的修正版代码；若 AI 修正失败，则会调用 `tryAlternativeFix` 执行规则级备用修复。整个过程会在最大重试次数内循环进行，直到验证成功或明确失败。

这一流程使 AI 生成能力从“只产出脚本文本”提升为“生成—执行—分析—修正—再验证”的闭环能力，是 NeonScan 2.0 的代表性创新实现。

### 5.10.4 自动扫描后的联动生成与验证实现

系统在 `main_autoscan_exploit_verify.go` 中实现了自动扫描后的联动流程：对 POC 扫描结果去重后，逐项构建 `ExpSpec`、生成初始 Python EXP、调用 `GenerateAndVerifyExp` 进行自动验证，并在成功后保存最终脚本。这样，自动扫描模块不再止步于“发现漏洞”，而是进一步进入“生成利用并验证可用性”的 2.0 工作流。

## 5.11 前端界面模块的详细设计实现

对应文件：`web/*.html`、`web/app.js`

前端采用静态多页面设计，每个功能模块对应独立页面，通过统一导航栏完成切换。页面中复用了任务表单、进度条、日志区、结果展示区等组件，使不同模块保持一致的交互风格。

前端通过 `EventSource` 连接 `/events` 接口接收 SSE 消息，并根据 `progress`、`find`、`end` 等不同类型更新页面状态。为了增强可用性，系统还将表单内容与运行中任务 ID 持久化到 `localStorage` 中，页面刷新后能够恢复表单状态并尝试重连正在执行的任务。

此外，系统还提供独立的报告页面，对端口、目录、POC、EXP、Web 探测、WAF 与资产收集结果进行统一汇总，并支持刷新、清空和导出。这使前端不仅是任务发起界面，也是最终结果查看与证据整理的重要载体。
