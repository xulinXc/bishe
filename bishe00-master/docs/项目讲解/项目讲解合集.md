# 项目讲解合集

这份文档是对 `docs/项目讲解/` 目录下各份说明材料的整合版本，目的是方便我直接交给老师、打印阅读、或者在答辩前集中复习。

内容按照“项目故事 -> 系统功能 -> 技术原理 -> 开发问题 -> 答辩表达”的顺序组织。

---

## 第一部分 项目是怎么一步步做出来的

### 1. 我一开始想做的其实不是现在这么大

这个项目最开始并不是一上来就想做成一个很完整的平台，而是想做一个和网络安全扫描相关的系统。最初的思路比较直接，就是希望能有一个页面，输入目标地址以后，系统去做一些基础扫描，把结果展示出来。那时候我的理解比较朴素，觉得“能扫出东西、能看到结果”就已经算完成了一部分。

一开始我更关注的是“功能有没有”，而不是“架构是不是特别规范”。所以项目的早期阶段，很明显是先把端口扫描、目录扫描、POC 扫描这些功能一个一个加进去。那个阶段的特点是：

1. 先追求功能跑通
2. 哪个功能需要，就先加哪个
3. 代码拆分和整体结构考虑得不够多
4. 很多地方是边测试边改

这也是为什么到了后面我自己会觉得项目有点乱，因为它确实不是从一开始就严格按一个很完整的软件工程流程从头设计好的，而是逐步生长出来的。

### 2. 为什么最后会选择 Go + 原生前端

这个项目最后的技术栈不是 Java Spring Boot，也不是 Vue，而是 Go 加原生 HTML、CSS、JavaScript。

从我现在回头看，之所以会形成这样的技术路线，主要有几个原因：

1. Go 本身适合做网络类和并发类任务，写扫描器比较直接
2. Go 编译和运行比较方便，部署一个 HTTP 服务也简单
3. 前端如果用原生页面，开发门槛更低，页面功能也够用
4. 项目重点其实不在复杂前端，而在后端扫描逻辑和功能整合

所以这个系统后来逐渐形成了这样的模式：

- 前端负责输入参数和显示结果
- 后端负责实际扫描和调度
- 前后端通过 HTTP 接口通信

### 3. 第一阶段：先把基础扫描能力做出来

我认为项目的第一阶段，是“基础扫描平台”的形成阶段。这个阶段最重要的不是 AI，也不是自动验证，而是先把几个最常用的扫描能力做起来。

#### 3.1 端口扫描

端口扫描可以理解为系统认识目标的第一步。因为一个目标主机到底开放了什么服务，往往先看端口。

比如：

- 22 端口通常可能是 SSH
- 80、443 可能是 Web 服务
- 3306 可能是 MySQL
- 8080、8000、8443 这些也可能是 Web 端口

所以我一开始先把端口扫描做了出来。这个功能的重要性在于，它相当于后面很多动作的前置判断。如果连端口都不知道，后面做 Web 探针、目录扫描、POC 扫描就没有明确目标。

#### 3.2 目录扫描

有了端口扫描以后，如果判断某个端口是 Web 服务，就可以进一步去扫目录。

目录扫描的意义是发现隐藏目录、后台路径、敏感文件等。

这个阶段我真正解决的问题是：

1. 用户输入一个目标 URL
2. 系统利用字典去尝试访问一批路径
3. 把有价值的路径结果展示出来

#### 3.3 POC 扫描

POC 扫描是项目进一步升级的关键一步。

POC 可以理解为“漏洞验证规则”或者“漏洞检测模板”。它和简单扫端口、扫目录不同，它是更贴近漏洞检测的。

这个阶段我做的事情，本质上是让系统支持读取不同格式的漏洞模板，然后根据模板去对目标发请求、校验返回结果，判断目标是否可能存在某个漏洞。

### 4. 第二阶段：系统开始从单点功能变成平台

如果说第一阶段只是把几个单功能堆起来，那么第二阶段开始，这个项目逐渐变成“一个统一的平台”。

这个变化主要体现在两个方面：

1. 有了统一的前端页面和模块导航
2. 有了统一的任务机制和实时进度推送

#### 4.1 前端页面逐渐完整

随着功能越来越多，我不可能每个功能都靠命令行操作，所以开始做页面。

后来前端逐渐形成了多个页面，比如：

- 端口扫描页面
- 目录扫描页面
- POC 扫描页面
- EXP 页面
- Web 探针页面
- WAF 绕过页面
- JS/URL 收集页面
- AI 分析页面
- 报告页面

这样系统看起来就不再像一堆零散脚本，而更像一个完整的软件。

#### 4.2 统一任务机制逐渐形成

扫描类任务有一个共同问题，就是它们通常不是瞬间完成的。比如端口扫描、目录扫描、POC 扫描，可能要跑几秒、几十秒，甚至更久。

如果前端发完请求以后，只能傻等，用户体验很差。所以项目后来逐渐形成了统一的任务机制：

1. 前端发请求
2. 后端创建任务 ID
3. 前端根据任务 ID 去订阅实时消息
4. 后端边执行边推送结果

这个机制一旦稳定下来，后面很多功能都能复用，所以它是系统从“功能集合”走向“平台”的关键一步。

### 5. 第三阶段：开始加入更有特色的高级功能

项目做到这里，如果只停留在基础扫描，其实已经可以作为一个普通扫描系统了。但为了让项目更有特色，也为了让整体更完整，后来又逐步加入了一些高级模块。

#### 5.1 Web 探针和指纹识别

有了端口扫描以后，如果发现某个端口可能是 Web 服务，还需要知道它到底是什么系统、什么技术栈。

所以后来加入了 Web 探针能力。这个功能会去访问页面，读取响应头、网页标题、部分页面内容，尝试识别技术栈和产品类型。

#### 5.2 WAF 绕过测试

后来为了增强系统的研究性和综合性，我又把 WAF 绕过测试加了进来。

这个模块的核心思路是：

1. 准备一些攻击 payload
2. 用不同的变形方式去改写 payload
3. 观察目标响应，看哪些变形可以绕过拦截

#### 5.3 JS 与 URL 信息收集

在 Web 安全里，前端资源本身经常藏着很多信息，比如 JS 文件里写死的接口路径、隐藏的 API 地址等。

所以后来我把 URL 收集、JS 分析、解包辅助相关能力也慢慢加了进去。

### 6. 第四阶段：AI 功能开始进入系统

这个阶段是项目变化最大的阶段之一。因为项目不再只是传统扫描，而开始加入 AI 相关能力。

#### 6.1 AI 分析

最先加入的是 AI 分析能力。简单说，就是把系统前面扫描出来的结果整理成一份报告，再交给 AI 生成分析结论。

#### 6.2 AI 生成 EXP

再往后，我开始让 AI 根据漏洞规则或检测结果生成 Python 利用脚本。

### 7. 第五阶段：从 AI 生成，继续发展到自动验证

单纯让 AI 生成代码，存在一个很现实的问题：AI 写出来的脚本不一定能直接用。可能有语法问题、URL 拼接问题、提取输出问题、参数问题。

所以后来我又继续往前走了一步：

1. AI 生成 Python EXP
2. 后端把脚本保存成临时文件
3. 调用本机 Python 去执行这个脚本
4. 判断脚本是否真的能利用目标
5. 如果失败，把失败原因再交给 AI 修正
6. 重复几轮，尽可能得到可用脚本

### 8. 第六阶段：自动化扫描工作流

当系统已经具备端口扫描、Web 探针、目录扫描、POC 检测、AI 分析之后，一个自然的想法就是：能不能让 AI 来帮我决定下一步做什么，而不是每次都手动点击。

于是后来项目又有了自动化扫描工作流，让 AI 基于已有结果去决定下一步操作。

### 9. 我现在怎么理解这个项目

如果现在让我用一句话总结，我会这样说：

这个项目是我围绕网络安全扫描这个主题，一步一步扩展出来的综合平台。最开始是基础扫描功能，后来逐渐加入统一页面、任务管理、实时结果推送，再继续加入 Web 探针、WAF 测试、JS 信息收集、AI 分析、AI 生成 EXP、自动验证和自动化扫描工作流，最后形成了现在这个综合性系统。

## 第二部分 系统现在到底做了什么

### 1. 系统整体定位

我会把它定义成：

**一个基于 Go 语言实现的综合性 Web 安全扫描与辅助分析平台。**

这个系统的核心目标，是围绕一个目标网站或目标主机，完成从基础信息收集、漏洞检测，到结果分析和利用验证的一整套流程。

### 2. 主要功能

#### 2.1 端口扫描

作用：扫描目标主机开放了哪些端口，判断目标可能提供了什么服务，为后续扫描提供基础信息。

#### 2.2 目录扫描

作用：利用字典批量探测目标网站可能存在的目录或文件，发现后台地址、敏感文件、接口路径等。

#### 2.3 POC 扫描

作用：利用漏洞模板去验证目标是否存在已知漏洞，通过规则化请求和响应匹配进行自动检测。

#### 2.4 EXP 验证

作用：根据规则对漏洞利用过程进行步骤化执行，验证漏洞是否可以被真正利用。

#### 2.5 Web 探针

作用：识别网页标题、响应头、协议、技术栈、指纹信息，对目标 Web 服务做更细致的识别。

#### 2.6 WAF 绕过测试

作用：针对 SQL 注入、XSS 等 payload 做多种变形，测试目标是否存在 WAF 拦截，以及某些变形是否可能绕过。

#### 2.7 JS 与 URL 信息收集

作用：结合外部工具分析站点中的 JS 和 URL 信息，发现接口、资源地址和隐藏路径。

#### 2.8 AI 分析

作用：将系统扫描得到的报告交给 AI，让 AI 生成更适合阅读的分析内容和总结。

#### 2.9 AI 生成 Python EXP

作用：根据漏洞规则或利用步骤，让 AI 生成 Python 利用脚本。

#### 2.10 AI 自动验证与修正

作用：自动执行 AI 生成的 Python 脚本，判断脚本是否真的可用，如果失败，再把错误信息交给 AI 修正。

#### 2.11 AI 自动化扫描工作流

作用：让 AI 结合当前扫描结果决定下一步调用什么工具，按流程自动推进扫描任务。

#### 2.12 扫描报告展示

作用：汇总端口扫描、目录扫描、POC、EXP、Web 探针、WAF、JS 收集等结果，在前端统一展示并导出。

### 3. 系统是怎么跑起来的

系统的工作方式可以概括成：

1. 前端页面在浏览器里打开
2. 浏览器通过 HTTP 向 Go 后端发请求
3. Go 后端收到请求后开始执行扫描任务
4. 后端通过 SSE 实时把进度和结果推送回前端
5. 前端持续更新页面内容

所以它最关键的两个交互机制是：

- 普通 HTTP 接口
- SSE 实时消息

## 第三部分 核心技术原理详细说明

### 1. 端口扫描原理

端口扫描的作用，是判断目标主机上哪些端口开放。

#### 1.1 TCP 与 UDP 区别

- TCP 是面向连接协议，需要先建立连接
- UDP 是无连接协议，直接发送数据，不保证对方回应

所以：

- TCP 扫描更容易判断开放状态
- UDP 扫描天然更难判断

#### 1.2 TCP 扫描实现思路

1. 获取端口列表
2. 尝试建立 TCP 连接
3. 在超时时间内成功连接则视为开放
4. 连接失败则视为关闭或不可达

#### 1.3 UDP 扫描实现思路

1. 向 UDP 端口发包
2. 观察是否收到响应
3. 收到响应则端口可能开放
4. 无响应则可能开放但静默，也可能关闭或被过滤

#### 1.4 Banner 抓取

在发现开放端口后，再尝试读取服务返回的初始信息，例如 SSH、HTTP 等标识，用于辅助判断服务类型。

### 2. 目录扫描原理

目录扫描本质上是字典爆破：

1. 准备路径字典
2. 逐个拼接目标 URL
3. 发起请求
4. 根据状态码、响应内容、长度等判断路径是否存在

之所以需要字典，是因为程序不可能凭空知道网站隐藏了哪些路径。

### 3. POC 扫描原理

POC 是规则化漏洞检测模板。它包含：

- 请求方法
- 请求路径
- 请求头
- 请求体
- 响应匹配条件

扫描流程是读取模板、解析规则、执行请求、判断响应是否符合漏洞特征。

POC 容易误报的原因，是某些响应特征并不是绝对唯一，因此必须收紧规则判断。

### 4. EXP 验证原理

EXP 偏向漏洞利用，而不只是检测。

项目中的 EXP 是多步骤结构，因为真实利用流程常常需要多次请求。每一步都可以包含：

- 方法
- 路径
- 请求头
- 请求体
- 验证规则
- 变量提取规则

变量提取的意义是把上一步响应中的 token、session、路径等动态值提取出来，用在下一步请求中。

### 5. Web 探针与指纹识别原理

Web 探针通过访问目标页面，收集：

- 页面标题
- 响应头
- Cookie
- 页面内容关键词
- favicon

指纹识别则利用这些特征与本地规则库比对，推测目标使用的技术栈或产品类型。

### 6. SSE 原理

SSE 是服务器向前端持续推送消息的机制。

它适合扫描系统的原因是：

1. 扫描任务通常耗时较长
2. 执行过程中会持续产生新结果
3. 用户希望实时看到进度和发现情况

项目中的流程是：

1. 前端发起任务
2. 后端返回 `taskId`
3. 前端用 `taskId` 建立 SSE 连接
4. 后端持续推送 `progress`、`find`、`end` 等消息

### 7. 并发与任务管理原理

扫描类任务适合并发，因为可以同时探测多个目标或端口。

但并发不能无限大，所以项目采用“有限并发”策略：

1. 提升速度
2. 控制资源消耗
3. 保持结果稳定

任务管理则用于保存：

- 任务 ID
- 总量
- 已完成数量
- 消息通道
- 停止信号

### 8. WAF 绕过测试原理

WAF 绕过测试的核心是研究 payload 经过编码、大小写变化、注释插入等变形后，是否还能绕过防护规则。

### 9. AI 分析原理

AI 分析本质上是：

1. 把扫描结果整理成结构化文本
2. 调用 AI 模型
3. 生成更自然的分析总结

### 10. AI 生成 Python EXP 原理

系统将漏洞规则、利用步骤和验证条件组织起来，交给 AI 生成 Python 脚本。选择 Python 的原因是它在利用脚本编写中很常见，requests 库也适合处理 HTTP 利用逻辑。

### 11. AI 自动验证与修正原理

自动验证流程是：

1. 保存 AI 生成代码
2. 调用本机 Python 运行
3. 捕获标准输出和错误输出
4. 判断是否真正命中漏洞标记和有效回显
5. 如果失败，把错误原因再交给 AI 修正

### 12. 自动化扫描工作流原理

它的目标是让 AI 根据已有扫描结果决定下一步调用什么工具，使整个扫描过程具备流程编排能力。

### 13. MCP 集成原理

MCP 让 AI 与外部工具连接，从而获得更多分析上下文和工具能力。在项目里主要体现为与 JADX 的联动。

## 第四部分 开发过程中遇到的问题和解决过程

### 1. 早期问题：功能能跑，但没有统一结构

项目早期最大的一个问题，不是某段代码报错，而是功能虽然一点点加上去了，但整体缺少统一结构。

后来逐渐引入了统一任务机制和统一前端控制逻辑，把很多扫描操作尽量放到一个一致的交互模型中：

1. 前端点击开始
2. 后端创建任务
3. 实时返回进度
4. 前端统一展示结果

### 2. 扫描类任务的实时反馈问题

端口扫描、目录扫描、POC 扫描这些任务都不是立刻完成的。如果前端发一个普通请求，只能等后端全部处理完再返回，用户体验很差。

后来采用了 SSE，让后端能够实时推送：

- 任务开始
- 当前进度
- 刚发现的结果
- 任务结束

### 3. POC 解析兼容性问题

随着接入越来越多的 POC 文件，开始发现很多模板并不能顺利解析。原因在于模板来源不同，字段和格式并不统一。

后续通过扩展字段兼容、区分模板风格、增加兜底解析逻辑来提升兼容性。

### 4. POC 误报问题

一开始 POC 扫描可能会扫出很多命中结果，但并不是每个都真的可靠。

后续通过收紧匹配逻辑，强化状态码、响应体、响应头和表达式判断，减少误报。

### 5. Python 执行和 AI EXP 验证问题

AI 生成 Python EXP 后，常见问题包括：

- Python 环境命令找不到
- 脚本语法报错
- URL 拼接错误
- 输出提取失败
- 看似成功但命令没有真正执行

后来把这块做成了完整闭环：生成、保存、执行、分析错误、交给 AI 修正、再次执行。

### 6. Windows 环境兼容问题

项目开发环境明显带有 Windows 场景，因此需要兼容不同 Python 命令、路径格式和工具行为。

### 7. JADX MCP 连接问题

MCP 相关功能不是一上来就稳定的。连接流程中出现过 406、502、连接慢、插件在线状态判断不清等问题。

后续通过补请求头、优化检测策略、加强错误提示来逐步修复。

### 8. Shouji 模块和外部工具集成问题

JS 与 URL 收集、解包辅助等能力依赖外部工具，常见问题包括路径找不到、工作目录不对、输出格式不稳定。

后续通过统一封装工具调用、固定路径查找逻辑、增加输出解析来改善。

### 9. 前端状态和报告汇总问题

系统功能越来越多以后，结果分散在不同页面，不利于展示和 AI 整体分析。

后来前端增加了统一报告数据结构，把多个模块结果汇总到一起，并保存在本地存储中。

### 10. 为什么代码里会留下很多日志和文档

因为很多功能是在不断实验、排错、修复中逐步稳定下来的，所以保留了较多调试日志和文档记录。虽然仓库看起来会复杂一些，但它也反映了项目的真实演进过程。

## 第五部分 我可以怎么向老师讲这个项目

### 1. 最简短版本

老师您好，我这个项目是一个基于 Go 语言实现的综合性 Web 安全扫描与辅助分析平台。系统前端采用原生 HTML、CSS、JavaScript 实现，后端通过 Go 提供 HTTP 接口，主要实现端口扫描、目录扫描、POC 漏洞检测、EXP 验证、Web 探针、WAF 绕过测试、JS 与 URL 信息收集、AI 分析以及 AI 生成和验证利用脚本等功能。项目的目标是把信息收集、漏洞检测、利用验证和结果分析整合到一个系统里。

### 2. 稍微完整一点的版本

我这个项目最开始并不是直接做成现在这么完整的平台，而是从基础扫描功能一点点往上扩展的。最开始先做端口扫描和目录扫描，后来加入 POC 扫描，让系统具备漏洞检测能力。再往后，为了提升系统完整性，我又加入了 Web 探针、WAF 绕过测试和 JS/URL 信息收集。最后结合 AI，又扩展了 AI 分析、AI 自动生成 Python EXP、自动验证和修正利用脚本等能力。现在整个系统已经形成了一条比较完整的流程，从目标发现、信息收集、漏洞检测，到利用验证和结果分析都能覆盖。

### 3. 如果老师问：你的系统和普通扫描器有什么区别

我会这样回答：

我这个系统和普通单功能扫描器的区别在于，它不是只做某一个点，而是把多个安全流程整合起来了。比如它不仅能做端口扫描，还能继续做 Web 探针、目录扫描、POC 检测，并把结果汇总成报告。更进一步，它还加入了 AI 分析和 AI 生成利用脚本的能力，甚至支持自动验证和失败修正，所以它更像一个综合性平台，而不只是一个单点工具。

### 4. 如果老师问：你为什么用 Go

我可以这样回答：

我选择 Go，主要是因为这个项目本质上是网络扫描和服务端调度类系统。Go 在网络请求处理、并发任务执行和 HTTP 服务实现方面比较直接，适合做这类系统。同时 Go 部署也比较方便，整体比较轻量，适合我的项目规模。

### 5. 如果老师问：你前端为什么不用 Vue，而用原生页面

我可以这样回答：

因为这个项目的重点不在复杂前端，而在后端扫描逻辑、任务调度和多模块整合。原生 HTML、CSS、JavaScript 已经足够支撑参数输入、结果展示、实时进度更新和报告汇总。这样可以让我把更多精力放在系统核心功能实现上。

### 6. 如果老师问：SSE 是什么，你为什么用了它

我可以这样回答：

因为扫描任务通常不是瞬间完成的，如果前端发起请求后一直等最终结果，用户会感觉系统卡住了。SSE 就是让服务器在任务执行过程中持续把进度和结果推送给前端，这样前端可以实时看到扫描进度、发现的新结果和任务完成状态。所以 SSE 在我这个系统里主要解决的是实时反馈问题。

### 7. 如果老师问：你项目里最有特点的地方是什么

我可以从三点说：

1. 系统把多个安全扫描能力整合在一起，不是单点工具
2. 系统支持实时任务反馈和报告汇总，交互体验更完整
3. 系统引入了 AI 分析、AI 生成利用脚本和自动验证修正机制，这部分比较有特色

### 8. 如果老师问：你这个项目开发过程中最大的难点是什么

最大的难点不是单个功能写不出来，而是随着功能越来越多，系统开始涉及很多不同链路，比如扫描任务调度、实时进度推送、漏洞规则解析、外部工具调用、AI 接口调用、Python 脚本执行和结果修正。很多问题都不是一个函数内部的问题，而是整条流程上的问题。所以我后面做的大量工作，其实是在不断把这些流程打通和稳定下来。
