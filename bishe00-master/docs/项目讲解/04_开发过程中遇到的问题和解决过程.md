# 开发过程中遇到的问题和解决过程

这部分我尽量按真实开发过程来写。因为这个项目不是一次性做成的，而是边做边改，所以问题很多，而且很多问题不是单个 bug，而是“随着系统越来越复杂，之前简单能跑的方法开始不够用了”。

## 1. 最早遇到的问题：功能能跑，但没有统一结构

项目早期最大的一个问题，不是某段代码报错，而是功能虽然一点点加上去了，但整体缺少统一结构。

表现出来就是：

1. 每个功能都能做一点
2. 但页面之间、接口之间、结果展示之间比较松散
3. 用户执行任务时，等待感很强
4. 不容易形成一个完整平台

### 我当时是怎么解决的

我后来逐渐引入了统一任务机制和统一前端控制逻辑，把很多扫描操作尽量放到一个一致的交互模型中：

1. 前端点击开始
2. 后端创建任务
3. 实时返回进度
4. 前端统一展示结果

这个改动虽然不是单个功能点，但对整个系统帮助很大，相当于给系统搭了骨架。

## 2. 扫描类任务的实时反馈问题

### 问题表现

端口扫描、目录扫描、POC 扫描这些任务都不是立刻完成的。如果前端发一个普通请求，只能等后端全部处理完再返回，用户会感觉：

1. 页面没反应
2. 不知道系统是不是卡住了
3. 不知道进度到哪了
4. 中间发现的结果也看不到

### 解决思路

我后来采用了 SSE。

### 解决后的效果

后端可以把以下内容实时推给前端：

- 任务开始
- 当前进度
- 刚发现的端口或漏洞结果
- 任务结束

### 这个问题让我学到的东西

我以前只知道“前端发请求，后端返回数据”，但做这个系统以后我真正意识到：

对于扫描类任务，实时反馈本身就是系统体验的一部分。SSE 不只是技术点，而是这个系统能够像“平台”而不是“脚本工具”那样工作的关键机制。

## 3. POC 解析兼容性问题

### 问题表现

随着我接入越来越多的 POC 文件，开始发现很多模板并不能顺利解析。尤其是不同来源的 YAML 模板，格式和字段并不完全统一。

具体问题包括：

1. 有些文件结构和预期不一样
2. 有些字段缺失或写法不同
3. 有些模板明明有价值，但因为解析太严格被跳过了

### 为什么会出现这个问题

因为漏洞模板并不是都严格统一的。有些像 X-Ray 风格，有些像 Nuclei 风格，还有一些文件缩进不规整或者使用旧字段。

### 我是怎么解决的

我逐步对解析逻辑做了兼容扩展：

1. 支持更多字段形式
2. 对不同模板格式做区分解析
3. 对部分异常情况增加兜底提取逻辑
4. 避免因为一个文件有问题就让整个扫描中断

### 结果

POC 的兼容性提高了，系统能处理的模板更多，也更适合毕业设计里强调“实用性和扩展性”。

## 4. POC 误报问题

### 问题表现

一开始 POC 扫描可能会扫出很多“命中结果”，但并不是每个都真的可靠。也就是误报比较多。

### 为什么这是个严重问题

因为一个安全扫描系统如果误报太多，结果就没有参考价值。数量再多也没有意义。

### 根因

从后来的整理看，原因主要在于：

1. 某些匹配条件太宽松
2. 空结果也可能被判成成功
3. 某些模板本身缺少足够严格的判定条件

### 我是怎么解决的

我逐步把匹配逻辑收紧：

1. 状态码判断更严格
2. bodyContains、headerContains 等条件更严格
3. 对没有有效匹配条件的模板不轻易认定为漏洞

### 我从这里学到什么

扫描系统不是“扫得多就好”，而是“结果可信更重要”。老师如果问我系统优化，我完全可以讲这点。

## 5. Python 执行和 AI EXP 验证问题

### 问题表现

当系统开始支持 AI 生成 Python EXP 以后，问题一下子多了起来。因为生成脚本只是第一步，脚本能不能执行、执行完能不能真的验证漏洞，才是真问题。

一开始常见的问题有：

1. Python 环境命令找不到
2. 脚本语法报错
3. URL 拼接错误
4. 请求虽然发出去了，但结果提取失败
5. 输出里看似有漏洞标记，但实际上命令没有真正执行

### 为什么这个问题复杂

因为这里已经不是单纯的 Go 逻辑了，而是跨了好几层：

1. Go 后端调度
2. AI 生成代码
3. Python 解释器执行
4. 目标网站返回结果
5. 系统再解析结果

任何一个环节出问题，最终都可能失败。

### 我是怎么解决的

后来我把这块做成了一个比较完整的闭环：

1. 先让 AI 生成脚本
2. 后端保存临时文件
3. 自动调用 Python 执行
4. 捕获标准输出和错误输出
5. 判断是否真的命中漏洞标记
6. 分析失败原因
7. 再把失败信息交给 AI 修正
8. 多轮尝试

### 这块的价值

这部分是我项目里比较有特色的能力。因为它不是停留在“生成代码”这个表面，而是尽量让生成的脚本实际可用。

## 6. Windows 环境兼容问题

### 问题表现

项目开发环境里有明显的 Windows 使用场景。很多脚本、命令、Python 调用在 Linux 思维下可以运行，但到了 Windows 下会出现问题。

比如：

1. `python3` 不一定存在，可能只有 `python` 或 `py`
2. 路径分隔符不一样
3. 某些 Python 模块在 Windows 上不可用或行为不同

### 我是怎么解决的

后面我对 Python 命令查找做了兼容：

1. 先尝试 `python`
2. 再尝试 `python3`
3. 再尝试 `py`

同时在生成 EXP 的提示词中，也强调不要依赖 Windows 上容易出问题的模块。

### 这说明了什么

说明系统不是只在理想环境里写代码，还考虑了本地实际运行条件，这也是工程实现的一部分。

## 7. JADX MCP 连接问题

### 问题表现

MCP 相关功能不是一上来就稳定的。特别是和 JADX 集成时，连接流程中出现过：

- 406
- 502
- 连接慢
- 插件在线状态判断不清楚

### 根因

这类问题往往不是单一代码错误，而是整条链路都要对：

1. Go 客户端请求格式要对
2. MCP 服务器要启动
3. JADX 侧插件要在线
4. 请求头和传输方式要匹配

### 我是怎么解决的

我在后续整理中把这类问题明确区分：

1. 哪些是客户端请求头问题
2. 哪些是服务器已经在运行但插件离线
3. 哪些是轮询过密导致连接慢

然后通过补请求头、优化检测策略、加强错误提示来逐步修复。

### 这块我应该怎么讲

我不需要假装自己一开始就完全懂 MCP，我更真实的表达应该是：

我在做这个功能时，逐步认识到它涉及多个组件之间的通信，不是简单连上一个接口就结束了，所以我通过不断调试请求头、连接方式和状态判断，把这条链路逐渐打通。

## 8. Shouji 模块和外部工具集成问题

### 问题表现

JS 与 URL 收集、解包辅助等功能很多依赖外部工具，不是纯 Go 代码就能解决。

这类功能常见问题包括：

1. 外部程序路径找不到
2. 工作目录不对
3. 工具输出格式不稳定
4. 输出是 HTML 报告，需要再次解析

### 我是怎么解决的

主要做法是：

1. 后端统一封装工具调用
2. 尽量固定工具路径查找逻辑
3. 增加输出解析逻辑
4. 把原始工具结果转换成系统内部更容易展示的格式

### 这块的意义

它体现了系统有一定“集成型开发”特点，不只是自己写功能，还要把外部能力接进来。

## 9. 前端状态和报告汇总问题

### 问题表现

系统功能越来越多以后，结果分散在不同页面。如果没有统一汇总，就会出现：

1. 用户看完一个页面就忘了另一个页面的结果
2. 老师演示时不好统一展示
3. 后续 AI 分析也缺少完整上下文

### 我是怎么解决的

后来前端增加了报告数据结构，把多个模块结果汇总到一起，并保存在本地存储中。

这样做之后：

1. 各模块结果能统一展示
2. AI 分析可以基于报告整体进行
3. 页面刷新后数据仍然可以恢复一部分

## 10. 为什么代码里会留下很多日志和文档

这是一个我自己很有感触的问题。

因为我很多功能并不是完全靠自己手写出来的，而是借助 AI 生成、再自己不断测试和修正。所以在这个过程中，我必须保留很多调试信息，才能判断到底是哪一层出了问题。

这就导致：

1. 代码里日志很多
2. 文档记录很多
3. 仓库里保留了很多修复说明

这从“仓库整洁度”来看确实不完美，但从“项目真实开发过程”来看，又非常真实。

如果老师问我为什么会这样，我可以坦诚地说：

这个项目很多功能是在不断实验、排错、修复中逐步稳定下来的，因此我保留了较多开发记录。这些记录虽然让仓库显得复杂，但也能反映我整个项目的演进过程和问题解决过程。

## 11. 我现在回头看，哪些问题最关键

如果让我总结几个最关键的问题，不是所有 bug 都要讲，而是讲最能体现项目成长的那几个：

1. 扫描任务没有实时反馈，所以引入 SSE
2. POC 模板兼容性不够，所以扩展了解析能力
3. POC 误报率高，所以收紧了判定逻辑
4. AI 生成的 EXP 不稳定，所以加入自动验证和修正
5. 外部工具与 MCP 接入复杂，所以逐步完善连接和错误处理
6. 结果分散，所以做了统一报告汇总

这几条其实已经足够构成一条完整的项目演进故事线。

## 12. 这部分我可以怎么向老师讲

如果老师问“你这个项目做的过程中最大的困难是什么”，我可以这样回答：

我这个项目最大的困难不是某一个功能写不出来，而是随着功能越来越多，系统开始涉及实时任务、规则解析、外部工具调用、AI 代码生成、Python 执行和结果修正等多条链路。很多问题不是单点问题，而是一个完整流程里任何一环出错都会影响结果。所以我后面做的很多工作，其实是在不断把这些链路打通、把结果做得更稳定、更可解释。

这句话很真实，也很符合你现在项目的情况。
