# 系统现在到底做了什么

## 1. 系统的整体定位

如果让我现在向老师介绍这个系统，我不会说它只是一个“扫描器”，因为它做的事情已经超过了普通扫描器。

我会把它定义成：

**一个基于 Go 语言实现的综合性 Web 安全扫描与辅助分析平台。**

这个系统的核心目标，是围绕一个目标网站或目标主机，完成从基础信息收集、漏洞检测，到结果分析和利用验证的一整套流程。

## 2. 它现在有哪些主要功能

### 2.1 端口扫描

作用：

- 扫描目标主机开放了哪些端口
- 判断目标可能提供了什么服务
- 为后续 Web 探针、目录扫描、POC 扫描提供基础信息

能解决的问题：

- 不知道目标开放了哪些服务
- 不知道后续该从哪个入口继续扫描

### 2.2 目录扫描

作用：

- 利用字典批量探测目标网站可能存在的目录或文件
- 发现后台地址、上传路径、敏感文件、接口路径等

能解决的问题：

- 网站表面看不出来的重要路径，往往可以通过字典爆破发现

### 2.3 POC 扫描

作用：

- 利用漏洞模板去验证目标是否存在已知漏洞
- 通过规则化请求、响应匹配、表达式判断进行自动检测

能解决的问题：

- 不只是“看到服务”，而是进一步判断“是否存在漏洞”

### 2.4 EXP 验证

作用：

- 根据规则对漏洞利用过程进行步骤化执行
- 验证漏洞是否可以被利用
- 提取回显信息或利用结果

能解决的问题：

- 区分“只是疑似漏洞”还是“真正可利用漏洞”

### 2.5 Web 探针

作用：

- 识别网页标题、响应头、协议、技术栈、指纹信息
- 对目标 Web 服务做更细致的识别

能解决的问题：

- 只知道某个端口开着还不够，还需要知道这个 Web 服务是什么技术、是什么系统

### 2.6 WAF 绕过测试

作用：

- 针对 SQL 注入、XSS 等 payload 做多种变形
- 测试目标是否存在 WAF 拦截，以及某些变形是否可能绕过

能解决的问题：

- 目标可能有防护，不同 payload 经过编码或变形后，拦截情况可能不同

### 2.7 JS 与 URL 信息收集

作用：

- 结合外部工具分析站点中的 JS 和 URL 信息
- 尝试发现接口、资源地址、隐藏路径、前端暴露信息

能解决的问题：

- 很多系统的接口信息藏在 JS 文件里，单纯看页面不容易发现

### 2.8 AI 分析

作用：

- 将系统扫描得到的报告交给 AI
- 让 AI 生成更适合阅读的分析内容和总结

能解决的问题：

- 原始扫描结果往往比较零散，AI 能帮助做归纳和表达

### 2.9 AI 生成 Python EXP

作用：

- 根据漏洞规则或利用步骤，让 AI 生成 Python 利用脚本
- 让系统从“发现漏洞”进一步走到“生成利用代码”

能解决的问题：

- 减少人工手写利用脚本的负担

### 2.10 AI 自动验证与修正

作用：

- 自动执行 AI 生成的 Python 脚本
- 判断脚本是否真的可用
- 如果失败，把错误信息交给 AI 继续修正

能解决的问题：

- AI 生成代码不一定一次成功，需要自动闭环修正

### 2.11 AI 自动化扫描工作流

作用：

- 让 AI 结合当前扫描结果决定下一步调用什么工具
- 按流程自动推进扫描任务

能解决的问题：

- 避免每一步都手动操作，提高整体自动化程度

### 2.12 扫描报告展示

作用：

- 汇总端口扫描、目录扫描、POC、EXP、Web 探针、WAF、JS 收集等结果
- 在前端统一展示并导出

能解决的问题：

- 把原来分散在不同页面、不同任务中的结果整理成一份总体材料

## 3. 系统是怎么跑起来的

这个系统不是传统那种前端项目一个进程、后端一个进程、数据库一个进程的复杂结构。它更偏向一个轻量的单体系统。

它的工作方式可以概括成：

1. 前端页面在浏览器里打开
2. 浏览器通过 HTTP 向 Go 后端发请求
3. Go 后端收到请求后开始执行扫描任务
4. 后端通过 SSE 实时把进度和结果推送回前端
5. 前端持续更新页面内容

所以它最关键的两个交互机制是：

- 普通 HTTP 接口
- SSE 实时消息

## 4. 现在系统的前端是什么样的

现在前端是多页面结构，不是单页面框架。

页面入口包括：

- 首页
- 端口扫描页
- 目录扫描页
- POC 扫描页
- EXP 页
- Web 探针页
- WAF 页
- JS/URL 收集页
- AI 分析页
- 扫描报告页
- JADX MCP 页

前端的作用不是做复杂渲染，而是：

1. 让用户输入参数
2. 发起后端任务
3. 订阅实时结果
4. 把结果展示出来
5. 本地保存报告数据

## 5. 现在系统的后端是什么样的

后端核心是一个 Go HTTP 服务。

它负责：

1. 注册所有扫描接口
2. 管理任务 ID
3. 管理实时消息通道
4. 处理端口、目录、POC、EXP、WAF、Web 探针等逻辑
5. 调用 AI 接口
6. 调用 Python 和外部工具

这意味着后端实际上是整个系统的大脑。

## 6. 系统现在的亮点在哪里

如果从老师的角度看，这个系统的亮点主要有下面几个：

1. 功能覆盖面比较广，不是单一模块
2. 扫描任务支持实时进度反馈，交互体验更完整
3. 支持多种规则化漏洞检测和利用验证
4. 加入了 AI 分析和 AI 生成利用脚本能力
5. 支持 AI 自动验证和修正脚本
6. 集成了外部工具和 MCP 能力，体现一定扩展性

## 7. 它现在还不是一个什么样的系统

为了让自己讲得更真实，我也要明确说明它目前还不是什么。

它目前还不是：

1. 一个面向生产环境的大型商用平台
2. 一个做了完整用户权限系统和数据库持久化的多用户系统
3. 一个所有模块都完全解耦、工程结构极其规范的项目

它更准确地说，是一个：

**围绕安全扫描和分析任务，逐步演进形成的综合性研究型系统。**

这个定位反而更符合毕业设计，因为它突出的是“功能研究、系统整合、工程实现和问题解决”。

## 8. 我现在最应该怎么概括这个系统

如果老师问我“你的系统到底做了什么”，我现在最适合的回答是：

我的系统围绕目标主机和目标网站，提供端口扫描、目录扫描、漏洞 POC 检测、EXP 验证、Web 指纹识别、WAF 绕过测试、JS 与 URL 信息收集、扫描报告汇总、AI 分析以及 AI 自动生成和验证利用脚本等功能，目标是把信息收集、漏洞检测、利用验证和分析说明整合到同一个平台中。
