# 项目是怎么一步步做出来的

## 1. 我一开始想做的其实不是现在这么大

这个项目最开始并不是一上来就想做成一个很完整的平台，而是想做一个和网络安全扫描相关的系统。最初的思路比较直接，就是希望能有一个页面，输入目标地址以后，系统去做一些基础扫描，把结果展示出来。那时候我的理解比较朴素，觉得“能扫出东西、能看到结果”就已经算完成了一部分。

一开始我更关注的是“功能有没有”，而不是“架构是不是特别规范”。所以项目的早期阶段，很明显是先把端口扫描、目录扫描、POC 扫描这些功能一个一个加进去。那个阶段的特点是：

1. 先追求功能跑通
2. 哪个功能需要，就先加哪个
3. 代码拆分和整体结构考虑得不够多
4. 很多地方是边测试边改

这也是为什么到了后面我自己会觉得项目有点乱，因为它确实不是从一开始就严格按一个很完整的软件工程流程从头设计好的，而是逐步生长出来的。

## 2. 为什么最后会选择 Go + 原生前端

这个项目最后的技术栈不是 Java Spring Boot，也不是 Vue，而是 Go 加原生 HTML、CSS、JavaScript。

从我现在回头看，之所以会形成这样的技术路线，主要有几个原因：

1. Go 本身适合做网络类和并发类任务，写扫描器比较直接
2. Go 编译和运行比较方便，部署一个 HTTP 服务也简单
3. 前端如果用原生页面，开发门槛更低，页面功能也够用
4. 项目重点其实不在复杂前端，而在后端扫描逻辑和功能整合

所以这个系统后来逐渐形成了这样的模式：

- 前端负责输入参数和显示结果
- 后端负责实际扫描和调度
- 前后端通过 HTTP 接口通信

这个思路一直保留到了现在。

## 3. 第一阶段：先把基础扫描能力做出来

我认为项目的第一阶段，是“基础扫描平台”的形成阶段。这个阶段最重要的不是 AI，也不是自动验证，而是先把几个最常用的扫描能力做起来。

### 3.1 端口扫描

端口扫描可以理解为系统认识目标的第一步。因为一个目标主机到底开放了什么服务，往往先看端口。

比如：

- 22 端口通常可能是 SSH
- 80、443 可能是 Web 服务
- 3306 可能是 MySQL
- 8080、8000、8443 这些也可能是 Web 端口

所以我一开始先把端口扫描做了出来。这个功能的重要性在于，它相当于后面很多动作的前置判断。如果连端口都不知道，后面做 Web 探针、目录扫描、POC 扫描就没有明确目标。

这个阶段我真正解决的问题是：

1. 用户输入一个主机和端口范围
2. 后端去批量测试端口连通性
3. 把开放端口结果返回给前端

它建立了系统最早的一条主线：前端发起任务，后端异步执行，前端持续看到结果。

### 3.2 目录扫描

有了端口扫描以后，如果判断某个端口是 Web 服务，就可以进一步去扫目录。

目录扫描的意义是发现隐藏目录、后台路径、敏感文件等。例如：

- `/admin`
- `/login`
- `/upload`
- `/api`
- 某些测试文件或配置文件

我后来把这个功能做进去，并且支持了字典文件。字典可以理解为系统拿着一堆常见路径去目标网站尝试访问，看哪些存在。

随着这个功能加入，系统就不再只是“扫端口”，而开始有点像真正的 Web 安全扫描系统了。

### 3.3 POC 扫描

POC 扫描是项目进一步升级的关键一步。

POC 可以理解为“漏洞验证规则”或者“漏洞检测模板”。它和简单扫端口、扫目录不同，它是更贴近漏洞检测的。

这个阶段我做的事情，本质上是让系统支持读取不同格式的漏洞模板，然后根据模板去对目标发请求、校验返回结果，判断目标是否可能存在某个漏洞。

这个功能把项目从“信息收集工具”往“漏洞检测系统”推进了一大步。

## 4. 第二阶段：系统开始从单点功能变成平台

如果说第一阶段只是把几个单功能堆起来，那么第二阶段开始，这个项目逐渐变成“一个统一的平台”。

这个变化主要体现在两个方面：

1. 有了统一的前端页面和模块导航
2. 有了统一的任务机制和实时进度推送

### 4.1 前端页面逐渐完整

随着功能越来越多，我不可能每个功能都靠命令行操作，所以开始做页面。

后来前端逐渐形成了多个页面，比如：

- 端口扫描页面
- 目录扫描页面
- POC 扫描页面
- EXP 页面
- Web 探针页面
- WAF 绕过页面
- JS/URL 收集页面
- AI 分析页面
- 报告页面

这样系统看起来就不再像一堆零散脚本，而更像一个完整的软件。

### 4.2 统一任务机制逐渐形成

扫描类任务有一个共同问题，就是它们通常不是瞬间完成的。比如端口扫描、目录扫描、POC 扫描，可能要跑几秒、几十秒，甚至更久。

如果前端发完请求以后，只能傻等，用户体验很差。所以项目后来逐渐形成了统一的任务机制：

1. 前端发请求
2. 后端创建任务 ID
3. 前端根据任务 ID 去订阅实时消息
4. 后端边执行边推送结果

这个机制一旦稳定下来，后面很多功能都能复用，所以它是系统从“功能集合”走向“平台”的关键一步。

## 5. 第三阶段：开始加入更有特色的高级功能

项目做到这里，如果只停留在基础扫描，其实已经可以作为一个普通扫描系统了。但为了让项目更有特色，也为了让整体更完整，后来又逐步加入了一些高级模块。

### 5.1 Web 探针和指纹识别

有了端口扫描以后，如果发现某个端口可能是 Web 服务，还需要知道它到底是什么系统、什么技术栈。

所以后来加入了 Web 探针能力。这个功能会去访问页面，读取响应头、网页标题、部分页面内容，尝试识别：

- 是不是 PHP、Java、.NET
- 是不是 WordPress、ThinkPHP、Spring 等
- 有没有 favicon 特征

这个功能对后面的目录扫描和 POC 扫描其实很重要，因为如果提前知道目标是什么技术栈，就可以更有针对性。

### 5.2 WAF 绕过测试

后来为了增强系统的研究性和综合性，我又把 WAF 绕过测试加了进来。

这个模块的核心思路是：

1. 准备一些攻击 payload
2. 用不同的变形方式去改写 payload
3. 观察目标响应，看哪些变形可以绕过拦截

这个功能体现的是系统不仅能“发现漏洞”，还能研究“防护绕过”的情况。

### 5.3 JS 与 URL 信息收集

在 Web 安全里，前端资源本身经常藏着很多信息，比如：

- JS 文件里写死的接口路径
- 隐藏的 API 地址
- 资源引用关系

所以后来我把 URL 收集、JS 分析、解包辅助相关能力也慢慢加了进去。这个部分不完全是自己从零写算法，很多地方是结合外部工具去做，再把结果接到我的系统中。

这也是为什么现在项目里不仅有自己写的扫描逻辑，还有一些外部工具集成。

## 6. 第四阶段：AI 功能开始进入系统

这个阶段是项目变化最大的阶段之一。因为项目不再只是传统扫描，而开始加入 AI 相关能力。

### 6.1 最开始为什么想加 AI

传统扫描的问题是，扫描结果出来以后，用户还需要自己看、自己理解、自己分析。如果目标复杂，信息很多，人工整理会很麻烦。

所以我后来开始想：能不能让 AI 帮我做这些事，比如：

- 根据扫描结果做分析
- 给出文字化总结
- 根据漏洞结果生成利用脚本
- 在自动化流程里帮助决策下一步扫描动作

这就把项目从“扫描工具”逐渐拉向“扫描 + 分析平台”。

### 6.2 AI 分析

最先加入的是 AI 分析能力。简单说，就是把系统前面扫描出来的结果整理成一份报告，再交给 AI 生成分析结论。

这样做的好处是：

1. 结果更容易看懂
2. 可以生成比较完整的文字总结
3. 更适合答辩和展示

### 6.3 AI 生成 EXP

再往后，我开始让 AI 根据漏洞规则或检测结果生成 Python 利用脚本。

这一步很有挑战，因为生成代码不只是“写几行文本”，而是要尽量让脚本能真的运行、真的对目标发请求、真的验证漏洞。

所以后来项目里又出现了“自动验证”和“失败后修正”的流程。

## 7. 第五阶段：从 AI 生成，继续发展到自动验证

这是我觉得项目最有特点的一块。

单纯让 AI 生成代码，存在一个很现实的问题：AI 写出来的脚本不一定能直接用。可能有语法问题、URL 拼接问题、提取输出问题、参数问题。

所以后来我又继续往前走了一步：

1. AI 生成 Python EXP
2. 后端把脚本保存成临时文件
3. 调用本机 Python 去执行这个脚本
4. 判断脚本是否真的能利用目标
5. 如果失败，把失败原因再交给 AI 修正
6. 重复几轮，尽可能得到可用脚本

到了这里，这个系统的特色就很明显了：

它不只是扫描，还能自动尝试生成和修复利用脚本。

## 8. 第六阶段：自动化扫描工作流

当系统已经具备端口扫描、Web 探针、目录扫描、POC 检测、AI 分析之后，一个自然的想法就是：能不能让 AI 来帮我决定下一步做什么，而不是每次都手动点击。

于是后来项目又有了自动化扫描工作流。

这个功能的思想是：

1. 先扫端口
2. 根据端口决定是不是有 Web 服务
3. 如果有 Web 服务，先做 Web 探针
4. 根据技术栈决定做什么 POC 扫描
5. 有需要再做目录扫描
6. 最后汇总结果并分析

也就是说，不再是单个功能独立跑，而是开始有“流程编排”的味道。

## 9. 为什么现在仓库会显得乱

我现在回头看，项目之所以显得乱，不是因为没有主线，而是因为它的成长轨迹太明显了。

具体体现在：

1. 功能是逐渐叠加的，不是一次性设计完
2. 开发过程中保留了很多调试文档
3. 为了排错加入了大量日志
4. 有些尝试过的功能后来改了方向，但痕迹还在
5. 上传文件、工具报告、测试文件都还留在仓库里

所以从我的角度讲，这个项目不是“从头规划好、一步不差地做出来”的，而是“围绕一个核心目标不断生长出来的”。

这个核心目标一直没有变，就是：

**做一个可以把信息收集、漏洞检测、利用验证、结果分析整合在一起的安全扫描系统。**

## 10. 我现在怎么理解这个项目

如果现在让我用一句话总结，我会这样说：

这个项目是我围绕网络安全扫描这个主题，一步一步扩展出来的综合平台。最开始是基础扫描功能，后来逐渐加入统一页面、任务管理、实时结果推送，再继续加入 Web 探针、WAF 测试、JS 信息收集、AI 分析、AI 生成 EXP、自动验证和自动化扫描工作流，最后形成了现在这个综合性系统。

从功能上看，它已经不是单点工具，而是一个平台。

从开发过程上看，它带有很强的演进痕迹，所以仓库里会留下很多阶段性内容。

但从系统主线来看，它现在已经可以清楚地概括为：

1. 前端页面负责交互
2. Go 后端负责扫描和调度
3. SSE 负责实时进度推送
4. 规则文件负责描述 POC/EXP
5. AI 负责分析和脚本生成
6. 外部工具负责增强能力

这就是我把项目从一开始做到现在的完整脉络。
