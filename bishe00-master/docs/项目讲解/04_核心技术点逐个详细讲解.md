## 1. 端口扫描

## 1.1 端口扫描是干什么的

端口扫描的作用，是判断目标主机上哪些端口开放，也就是哪些网络服务可能正在运行。

可以把一台主机理解成一栋楼，IP 地址是楼的地址，端口就是楼里的房间号。不同网络服务通常监听不同端口。

常见例子：

- `22` 端口常见是 SSH
- `80` 端口常见是 HTTP
- `443` 端口常见是 HTTPS
- `3306` 端口常见是 MySQL
- `8080`、`8443` 等也经常是 Web 服务

所以端口扫描是整个系统的入口。它回答的是最基础的问题：

**这个目标到底暴露了哪些服务入口？**

如果连入口都不知道，后面的 Web 探针、目录扫描、POC 检测都没有明确对象。

## 1.2 为什么有 TCP 和 UDP

这是老师很容易追问的点。

### TCP 是什么

TCP 是面向连接的协议。所谓“面向连接”，意思是通信双方正式传输数据之前，需要先建立连接。

最常见的说法叫“三次握手”，简单理解就是：

1. 客户端先说“我想连你”
2. 服务端回应“可以连”
3. 客户端再确认“好，我开始连”

建立成功后，双方才开始正常传数据。

从扫描角度看，TCP 的好处是：

- 如果端口开放，通常可以更容易建立连接
- 如果端口关闭，通常会快速失败

所以 TCP 扫描更直接、更容易判断。

### UDP 是什么

UDP 是无连接协议。它不像 TCP 那样先建立连接，而是直接把数据发出去。

从扫描角度看，UDP 的困难在于：

- 发出去的数据，不保证对方一定会回
- 对方不回，不一定说明端口关闭
- 有些服务即使开放，也可能在特定格式下才回复

所以 UDP 扫描天生比 TCP 难判断。

### 用一句话区分

- TCP 像打电话，要先接通
- UDP 像寄一张明信片，直接发出去，不保证对方回复

因此：

- TCP 扫描结果相对更明确
- UDP 扫描结果常常只能说“可能开放”“可能关闭”“可能被过滤”

## 1.3 端口扫描的基本实现原理

### TCP 扫描原理

在我的项目里，TCP 扫描采用的是比较直接的连接探测方式。

流程可以概括为：

1. 读取用户输入的目标主机和端口范围
2. 把端口范围解析成一个具体的端口列表
3. 对每个端口尝试建立 TCP 连接
4. 如果在超时时间内连接成功，就认为端口开放
5. 如果连接失败，就认为端口关闭或不可达

这种方式的优点是：

1. 实现简单
2. 适合作为毕业设计中的实用扫描功能
3. 结果比较容易解释给老师听

### UDP 扫描原理

UDP 不能靠“连接成功”来判断，因此常见做法是：

1. 向目标 UDP 端口发送数据包
2. 观察是否收到响应
3. 如果收到特定响应，说明端口可能开放
4. 如果没有响应，可能是开放但静默，也可能是关闭或被过滤

所以在解释时我要强调：

**UDP 扫描不如 TCP 扫描确定，这是协议本身决定的，不是代码写得不好。**

## 1.4 什么是超时控制

如果系统一直等某个端口返回结果，扫描就会卡住。因此需要设置超时时间。

超时控制的意义是：

1. 避免某个端口响应太慢拖累整体扫描
2. 让整个任务有可预测的执行时间
3. 让系统可以在速度和准确性之间做平衡

例如：

- 超时太短，可能把慢响应端口误判成关闭
- 超时太长，整体扫描会变慢

所以超时本质上是一种工程取舍。

## 1.5 什么是 Banner 抓取

发现端口开放后，只知道“这里有服务”还不够，还希望进一步知道“可能是什么服务”。

Banner 抓取就是在连接成功后，再尝试读取一点服务返回的初始信息。

例如可能读到：

- `SSH-2.0-OpenSSH_8.2`
- HTTP 响应头
- 某些数据库、中间件或代理服务暴露的标识

它的意义在于：

- 开放端口只能说明“有服务”
- Banner 能帮助判断“是什么服务”

这对后续分析很有帮助。

## 1.6 我这个项目中的实现方式

项目后端会接收这些参数：

- `host`
- `ports`
- `concurrency`
- `timeoutMs`
- `scanType`
- `grabBanner`

然后流程是：

1. 解析端口范围，例如 `1-1024,3306,8080`
2. 将其转换为实际端口列表
3. 根据 `scanType` 选择 TCP 或 UDP 扫描逻辑
4. 每扫完一个端口就更新进度
5. 若发现开放端口，则通过 SSE 把结果推送到前端
6. 如果启用了 Banner 抓取，则继续尝试读取服务标识

## 1.7 为什么端口扫描必须支持并发

如果一个端口一个端口顺序扫描，会非常慢。

例如扫描 1000 个端口，即使每个端口只等待几百毫秒，总耗时也会很大。

所以项目里使用并发：

1. 同时探测多个端口
2. 用一个并发上限控制同时运行的扫描数量

这样可以明显提高扫描速度。

## 1.8 为什么并发不能无限大

很多人会以为并发越高越好，但实际上不是。

如果并发太高，会出现：

1. 本机资源消耗上升
2. 网络拥塞
3. 对目标造成过大压力
4. 扫描结果不稳定
5. 前端接收和展示结果也会变得混乱

所以系统允许用户设置并发，但不会无上限地扩张。

## 1.9 端口扫描在全系统中的位置

端口扫描不只是一个独立功能，它是后续流程的重要前置步骤。

它输出的结果会影响：

1. 是否需要进行 Web 探针
2. 哪些 URL 需要继续测试
3. 后续目录扫描和漏洞扫描的重点对象

换句话说，端口扫描负责“先摸清目标的入口”。

## 2. 目录扫描

## 2.1 目录扫描是干什么的

目录扫描的目标，是发现网站中没有直接暴露在首页上的路径或文件。

这些路径可能包括：

- 后台登录地址
- 上传目录
- 接口路径
- 测试页面
- 调试页面
- 配置文件
- 备份文件

很多重要信息并不会直接出现在首页链接中，所以目录扫描是 Web 安全里非常常见的一步。

## 2.2 它的基本原理是什么

目录扫描的核心原理就是“字典爆破”。

意思是：

1. 准备一份常见路径的字典
2. 把字典中的每一项拼接到目标 URL 后面
3. 向这些路径发起 HTTP 请求
4. 根据响应判断哪些路径真实存在

例如：

- 目标是 `http://test.com`
- 字典里有 `admin`
- 程序就会访问 `http://test.com/admin`

## 2.3 为什么目录扫描必须依赖字典

因为程序不可能凭空知道目标网站隐藏了什么路径。

目录扫描本质上是一种“基于经验集合的猜测”。这个经验集合就是字典。

字典来源通常有三种：

1. 内置通用字典
2. 特定技术栈字典
3. 用户自己提供的字典

## 2.4 为什么不同状态码都可能有价值

目录扫描时，不是只有 `200 OK` 才有意义。

很多情况下：

- `200` 表示路径存在并可访问
- `301/302` 表示路径存在但发生了跳转
- `403` 表示路径存在但被禁止访问

所以老师如果问为什么有些 `403` 也会被记录，我可以说：

**因为 403 说明路径很可能真实存在，只是当前权限不能访问。**

## 2.5 为什么目录扫描会有误报

有些网站会把所有不存在的路径统一返回同一个页面，例如：

- 不管访问什么，都返回一个 200 页面
- 页面长度和内容几乎一样

这样就可能导致“看起来每个路径都存在”，产生误报。

所以目录扫描不仅要看状态码，还要结合：

- 响应长度
- 页面内容
- 特征差异

## 2.6 我这个项目里怎么实现目录扫描

项目中的目录扫描流程大致是：

1. 前端输入目标地址
2. 选择内置字典或上传自定义字典
3. 后端逐行读取字典项
4. 将字典项拼接成完整 URL
5. 发送请求并分析响应
6. 发现有价值结果后通过 SSE 推送给前端

## 2.7 为什么目录扫描适合和指纹识别结合

不同技术栈常见路径不一样。

例如：

- PHP 项目可能有某类路径
- Java Web 项目可能有另一类路径
- WordPress、ThinkPHP、Spring Boot 也各有特征路径

所以如果 Web 探针先识别出技术栈，再选择对应字典，目录扫描效率和命中率都会更高。

## 3. POC 扫描

## 3.1 POC 是什么

POC 的核心作用是“验证目标是否存在某个漏洞”。

它通常不是完整利用代码，而是一种规则化的检测模板。

POC 想回答的问题是：

**这个目标有没有漏洞迹象？**

## 3.2 一个 POC 通常包含什么

一个 POC 里一般会包含这些内容：

1. 请求方法，例如 GET、POST
2. 请求路径
3. 请求头
4. 请求体
5. 匹配条件，例如状态码、响应头、响应体中的关键字

也就是说，POC 本质上是在描述：

“我应该怎么请求目标，以及收到什么响应才算命中漏洞特征。”

## 3.3 为什么项目里要支持多种 POC 格式

因为现有的漏洞模板来源并不统一。

项目里实际兼容了多种风格：

- 自定义 POC
- X-Ray 风格 POC
- Nuclei 风格 POC

支持多种格式的意义是：

1. 能复用更多现成模板
2. 能覆盖更多漏洞规则
3. 体现系统的扩展能力

## 3.4 POC 扫描的原理是什么

POC 扫描流程大致是：

1. 读取 POC 文件
2. 解析成系统内部的数据结构
3. 按规则向目标发起请求
4. 对响应进行匹配判断
5. 满足条件则判定命中

匹配常见方式包括：

1. 状态码匹配
2. 响应体关键字匹配
3. 响应头关键字匹配
4. 布尔表达式组合判断

## 3.5 为什么 POC 扫描容易误报

因为很多响应特征并不是完全唯一的。

例如：

- 某个关键字在正常页面也可能出现
- 某个 200 响应并不一定说明漏洞存在
- 某些模板条件过于宽松

所以 POC 扫描最大的难点之一不是“能不能跑”，而是“命中结果是否可信”。

## 3.6 我在项目里是怎么处理兼容性问题的

随着我接入更多模板，我发现不同模板：

- 字段名不一样
- 缩进风格不一样
- 有些格式甚至不完全规范

所以项目里后来做了更多兼容处理：

1. 扩展可识别字段
2. 区分不同模板风格
3. 对一些格式异常情况做兜底提取
4. 对无法解析的模板自动跳过，不让整个扫描中断

## 3.7 为什么误报优化很重要

安全扫描系统的价值不在于“扫出很多”，而在于“扫出来的结果可信”。

所以后面我对判定逻辑做了收紧：

1. 更严格地看状态码
2. 更严格地看 bodyContains 和 headerContains
3. 对缺少有效匹配条件的模板不轻易判真

这部分很适合答辩时讲“系统优化”。

## 4. EXP 验证

## 4.1 EXP 和 POC 的区别

如果说 POC 是“验证漏洞是否存在”，那么 EXP 更偏“真正去利用漏洞”。

POC 回答的是：

**有没有漏洞迹象。**

EXP 回答的是：

**如果存在这个漏洞，我能不能进一步利用。**

## 4.2 为什么项目中的 EXP 是多步骤结构

真实漏洞利用往往不是一次请求就完成。

例如可能需要：

1. 第一步先获取某个动态参数
2. 第二步带着参数发利用请求
3. 第三步再访问某个路径验证结果

所以项目中的 EXP 不是简单一条请求，而是一个多步骤流程。

每一步都可以包含：

- 请求方法
- 请求路径
- 请求头
- 请求体
- 验证规则
- 变量提取规则

## 4.3 什么是变量提取

变量提取是多步骤利用里的关键技术点。

意思是：

前一个请求的响应中，可能包含后一个请求要使用的动态值，例如：

- token
- session id
- 文件路径
- 验证码结果

系统通过规则从响应中提取这些值，再替换到后续请求中。

这样一个 EXP 才能从“静态模板”变成“可执行的利用流程”。

## 4.4 EXP 验证为什么重要

因为仅仅发现漏洞特征，还不一定说明漏洞真的能被利用。

EXP 验证的意义是：

1. 进一步提高结果可信度
2. 判断漏洞实际风险是否更高
3. 为后续 AI 生成利用脚本提供基础数据

## 5. Web 探针与指纹识别

## 5.1 Web 探针是做什么的

Web 探针的目标，是在发现 Web 服务之后，快速识别它的基本信息。

通常会收集：

- 页面标题
- 响应头
- 协议版本
- 页面长度
- favicon
- robots.txt
- 技术栈特征

## 5.2 为什么光知道端口开放还不够

因为端口开放只说明“这里有个 Web 服务”，但后续想做更精确的扫描，需要知道：

- 这是 PHP 还是 Java
- 可能是 WordPress 还是 ThinkPHP
- 有没有明显的产品特征

这就是 Web 探针的意义。

## 5.3 指纹识别的原理是什么

很多系统会在这些地方留下特征：

- 响应头
- Cookie
- 页面源码
- favicon
- 特定关键词

系统通过指纹规则去匹配这些特征，如果命中，就推测目标属于某种技术栈或产品。

## 5.4 favicon hash 是什么

有些系统的 favicon 图标比较固定，因此可以：

1. 下载 favicon.ico
2. 对文件计算哈希值
3. 与已知指纹库比对

如果哈希匹配，就说明目标可能是某个已知产品。

## 5.5 我这个项目里如何实现

项目中的 Web 探针会：

1. 请求目标 URL
2. 提取页面标题
3. 读取响应头中的 `Server`、`X-Powered-By` 等信息
4. 分析 Cookie 特征
5. 在需要时下载 favicon 计算哈希
6. 将这些信息和本地指纹库进行匹配

这样系统能输出一组比较直观的技术栈信息。

## 6. 文件上传与资源管理

## 6.1 为什么系统里需要上传功能

因为很多扫描能力都依赖用户提供的文件，例如：

- 自定义字典
- POC 文件
- EXP 文件
- 工具处理所需的输入文件

所以系统不能只靠固定内置资源，也需要支持上传。

## 6.2 上传模块的作用

上传模块负责：

1. 接收前端文件
2. 保存到服务器本地目录
3. 返回可用路径给其他模块继续使用

## 6.3 为什么还要做清理机制

因为上传目录本质上属于运行时产物，如果一直不清理，会导致：

1. 文件越来越多
2. 仓库和运行目录越来越乱
3. 磁盘占用增加

所以项目里会对较旧的上传文件做清理。

## 7. SSE 实时推送

## 7.1 SSE 是什么

SSE 全称是 `Server-Sent Events`，中文可以理解为“服务器向前端持续推送事件”。

普通 HTTP 请求通常是：

1. 前端发请求
2. 后端处理
3. 一次性返回结果
4. 连接结束

但扫描任务不是瞬时完成的，所以这种模式不适合本项目。

## 7.2 为什么扫描系统适合 SSE

扫描任务的特点是：

1. 执行时间较长
2. 中途会不断产生新结果
3. 用户希望实时看到进度

SSE 刚好适合这种“后端不断往前端推消息”的场景。

## 7.3 为什么不用轮询

轮询的意思是前端每隔几秒自己去问一次后端：“任务做完了吗？”

轮询的问题是：

1. 请求很多，效率不高
2. 实时性一般
3. 实现上不够优雅

相比之下，SSE 是后端主动推送，更适合持续输出进度和发现结果。

## 7.4 为什么不用 WebSocket

WebSocket 也能做实时通信，而且更强大，因为它支持双向通信。

但在我的项目里，扫描场景主要是：

- 前端发起一次任务
- 后端持续推送进度

也就是说，主要需求是“单向推送”，不是复杂的实时双向交互。

因此 SSE 更轻量，也更适合这个系统。

## 7.5 我这个项目里的实现方式

项目里的典型流程是：

1. 前端先请求某个扫描接口
2. 后端创建一个任务并返回 `taskId`
3. 前端根据 `taskId` 建立 SSE 连接
4. 后端执行任务时不断通过这个连接发送消息
5. 前端接收消息并更新页面

## 7.6 项目里 SSE 消息有哪些类型

典型消息包括：

- `start`：任务开始
- `progress`：进度变化
- `find`：发现了结果
- `end`：任务结束
- `ping`：心跳包

这样前端就不只是“等结果”，而是能看到整个执行过程。

---

## 8. 任务管理与并发控制

## 8.1 为什么需要任务管理

扫描不是瞬时操作，而且系统里可能同时存在多个扫描任务。

因此系统需要统一任务结构来记录：

- 任务 ID
- 总工作量
- 已完成数量
- 消息通道
- 停止信号
- 创建时间

有了任务结构，前端和后端才能围绕同一个任务对象沟通。

## 8.2 什么是异步任务

异步任务就是：

前端发起操作后，后端并不会让整个页面一直阻塞等待，而是把这个操作放到后台执行，前端通过任务 ID 去跟踪执行过程。

这比“页面卡死等最终结果”更适合扫描系统。

## 8.3 为什么要支持停止任务

因为有些扫描任务时间较长，用户可能：

- 输错目标
- 改变扫描范围
- 不想继续等待

所以系统中不仅要有“开始”，还要有“停止”，这样平台才更完整。

## 8.4 什么是有限并发

项目里虽然要并发执行多个扫描动作，但并不是无限制开启。

有限并发的意义是：

1. 控制资源消耗
2. 避免本机或目标压力过大
3. 保持整体任务稳定

从工程角度说，这是一种平衡速度和稳定性的做法。

## 9. WAF 绕过测试

## 9.1 WAF 是什么

WAF 全称是 Web Application Firewall，也就是 Web 应用防火墙。

它的作用是拦截疑似攻击请求，例如：

- SQL 注入
- XSS
- 一些恶意 payload

## 9.2 WAF 绕过测试是做什么的

它要研究的问题是：

**同一个攻击 payload，如果稍微变形，是否还能绕过防护。**

## 9.3 为什么 payload 要做变形

很多 WAF 规则本质上是基于特征匹配的。

例如可能会拦截：

- `union select`
- `<script>`

如果把这些内容进行：

- URL 编码
- 双重编码
- 大小写变化
- 注释插入
- HTML 实体编码

某些简单规则就可能失效。

## 9.4 这个模块在项目中的意义

它体现的是：

系统不仅做“检测”，还做一定程度的“对抗测试”和“安全研究”。

---

## 10. JS 与 URL 信息收集

## 10.1 为什么要分析 JS 和 URL

很多前端站点会在 JS 文件里暴露：

- 接口路径
- API 地址
- 资源地址
- 某些隐藏页面信息

这些内容在页面上不一定能直接看出来，但在 JS 里常常能找到。

## 10.2 这个模块的原理是什么

这部分很多能力并不是完全自己从零实现，而是结合外部工具来做。

整体思路是：

1. 下载或分析目标页面相关资源
2. 提取其中的 JS、URL、接口信息
3. 将外部工具结果统一整理为系统内部可展示的数据

## 10.3 为什么这部分属于“集成能力”

因为它更多体现的是：

1. 系统如何调用外部工具
2. 如何解析工具输出
3. 如何把工具结果纳入自己的平台展示

这类能力在毕业设计里可以体现“系统整合能力”。

## 11. AI 分析

## 11.1 为什么要引入 AI 分析

传统扫描结果往往比较零散：

- 有端口
- 有目录
- 有漏洞命中
- 有指纹结果

但这些原始结果不一定容易直接阅读。

所以引入 AI 分析的目的，是把这些结果整理成更自然、更像报告的总结。

## 11.2 它本质上做了什么

本质流程是：

1. 系统先把扫描结果整理成结构化数据
2. 再把这些数据转成适合 AI 理解的文本
3. 调用 AI 接口生成分析结果

也就是说，AI 分析并不是替代扫描，而是基于扫描结果做“二次理解和表达”。

## 11.3 这一块的价值是什么

它的价值不在于“AI 很高级”，而在于：

1. 帮助用户更快理解结果
2. 帮助老师更快看到系统输出的意义
3. 为后续自动化流程提供分析基础

---

## 12. AI 生成 Python EXP

## 12.1 为什么要让 AI 生成利用脚本

因为手写利用脚本成本较高，而且很多利用逻辑其实可以从漏洞规则中推导出来。

所以系统尝试把：

- 漏洞名称
- 漏洞利用建议
- 请求步骤
- 参数占位符
- 验证条件

这些内容整理后交给 AI，让 AI 输出 Python 代码。

## 12.2 为什么选 Python

因为 Python 在漏洞利用脚本场景中很常见：

1. 写 HTTP 请求方便
2. 文本处理方便
3. requests 库生态成熟
4. AI 生成这类代码也更自然

所以项目里出现了“Go 平台 + Python 利用脚本”的组合。

## 12.3 为什么这部分不能只停留在生成文本

因为 AI 生成出来的代码不一定真的能运行。

如果只把代码打印出来，那它更像一个“代码草稿生成器”；但如果能继续执行和验证，它才更接近真正可用的利用能力。

---

## 13. AI 自动验证与修正

## 13.1 为什么生成后还要验证

AI 生成代码后，常见问题包括：

- 语法错误
- 参数错误
- URL 拼接错误
- 请求逻辑不完整
- 提取输出失败
- 看似成功但实际没利用到目标

所以必须做“生成后验证”。

## 13.2 自动验证的基本流程是什么

项目中的自动验证流程大致是：

1. 把 AI 生成的 Python 代码保存成文件
2. 调用本机 Python 去执行
3. 读取标准输出和错误输出
4. 检查是否出现预期的漏洞标记和有效回显
5. 如果失败，分析错误原因
6. 把错误原因再交给 AI 进行修正
7. 再次执行，形成多轮闭环

## 13.3 为什么这一步是项目亮点

因为它说明系统不是只让 AI“写一段看起来像代码的东西”，而是尽量逼近“生成能实际运行的代码”。

这在答辩时很适合作为特色功能去讲。

---

## 14. AI 自动化扫描工作流

## 14.1 这个功能是做什么的

它的目标不是单独执行某一个扫描功能，而是让 AI 结合已有结果，自动决定下一步该做什么。

例如：

1. 先扫端口
2. 发现 Web 端口后做 Web 探针
3. 识别技术栈后做针对性 POC 扫描
4. 有需要再做目录扫描
5. 最后汇总并生成分析结果

## 14.2 它和普通扫描接口有什么区别

普通接口是“人明确点哪个功能就执行哪个”。

自动化扫描工作流则是：

**由 AI 在多步流程中参与决策。**

也就是说，它更像一个编排器或调度流程，而不只是一个单点工具。

## 14.3 为什么要给 AI 定义工具

因为 AI 不能直接随便操作后端，它必须通过系统提供的“可调用工具”来完成动作。

这些工具相当于系统给 AI 开放的一组能力，例如：

- `port_scan`
- `web_probe`
- `dir_scan`
- `poc_scan`

这样既让 AI 能参与决策，又不会失去系统边界。

## 15. MCP 集成与 JADX 联动

## 15.1 MCP 是什么

MCP 可以理解为一种让 AI 与外部工具协同工作的机制。

在这个项目里，MCP 主要和 JADX 集成相关。

## 15.2 为什么需要 MCP

如果 AI 只是单纯聊天，它并不知道本地逆向工具里的信息。

通过 MCP，AI 可以：

1. 连接到外部分析工具
2. 获取更多上下文
3. 调用工具能力

这样系统的能力就从 Web 扫描扩展到了逆向辅助分析。

## 15.3 这一块为什么调试难

因为 MCP 涉及多个组件：

1. Go 客户端
2. MCP 服务端
3. 外部工具本体
4. 某些插件或内部连接

只要其中任何一环状态不对，就会出现连接错误、超时、请求头不匹配等问题。

所以这块更像“系统集成问题”，而不是单纯的代码语法问题。

## 16. 前端报告汇总机制

## 16.1 为什么需要报告汇总

如果每个功能只在自己的页面显示结果，那老师在看系统时会觉得结果很分散。

例如：

- 端口扫描结果在一页
- POC 扫描结果在另一页
- WAF 结果又在另一页

这样不利于展示，也不利于 AI 做整体分析。

## 16.2 这个项目怎么做报告汇总

项目前端维护了一份统一的报告数据结构，把多个模块结果收集到一起，并存入本地存储。

这样做的好处是：

1. 各模块结果可以集中展示
2. 页面刷新后能恢复一部分数据
3. AI 分析时可以基于整体报告而不是单点结果

## 16.3 为什么这里没有做数据库持久化

因为这个项目当前更偏研究型和单机演示型系统，重点在功能链路和模块整合，而不是多用户长期数据管理。

所以目前报告更偏“浏览器本地会话级汇总”，而不是正式的后端数据库报表系统。

## 17. 我答辩时最该讲熟的几个技术点

如果老师追问技术细节，我最应该讲熟的是下面这些：

1. 端口扫描为什么要分 TCP 和 UDP
2. 为什么 TCP 更容易判断开放，UDP 更难判断
3. 目录扫描为什么依赖字典，为什么会有误报
4. POC 为什么本质上是规则化漏洞检测
5. EXP 为什么要多步骤、为什么需要变量提取
6. Web 指纹识别为什么能靠响应头、关键词和 favicon
7. SSE 为什么适合扫描系统，为什么不用轮询
8. 并发为什么能提速，为什么又不能无限大
9. AI 生成代码为什么还要自动验证和修正
10. 自动化扫描工作流为什么体现了系统的智能化调度能力

只要我把这些点讲清楚，老师基本就能看出我已经对整个项目形成了结构化理解，而不只是知道每个按钮的作用。
